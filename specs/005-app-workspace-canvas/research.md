# 研究记录：应用工作空间与编排画布

## 决策 1：工作空间采用“每个用户自动拥有一个个人默认工作空间”

- Decision: 已登录用户访问工作空间入口时，如果还没有个人默认工作空间，后端在受保护用例中自动创建并返回该工作空间。
- Rationale: 规格要求“登录后默认进入自己的工作空间”，澄清结果也要求首次登录无工作空间时自动创建。把初始化放在后端用例中可保证前端刷新、直接访问和 API 调用都得到一致行为，并避免前端重复判断。
- Alternatives considered:
  - 前端检测无工作空间后再发起创建：会产生额外往返和并发重复创建风险。
  - 用户手动创建工作空间：不符合已确认的默认进入体验。
  - 管理员预创建：超出个人工作空间首版范围。

## 决策 2：工作空间与应用都由当前认证用户隔离

- Decision: 所有 `/api/workspace` 接口从 HTTP Only Cookie 会话解析当前用户，并在查询、创建、编辑和详情读取中强制使用当前 `user_id` 作为作用域。
- Rationale: 规格要求用户只能看到和操作自己的工作空间内容。复用现有认证会话可避免新增认证机制，也能让契约测试直接验证跨用户隔离。
- Alternatives considered:
  - 由前端传入 `user_id`：容易伪造，违反安全边界。
  - 使用全局工作空间：不符合个人空间需求。
  - 先不做权限隔离：会直接违反 FR-002 和安全要求。

## 决策 3：应用名称唯一范围限定为所属工作空间

- Decision: 在同一 `workspace_id` 内应用名称必须唯一；不同工作空间之间允许重名。创建和编辑名称时都执行该约束。
- Rationale: 澄清结果要求同一工作空间内不允许同名，这能保证卡片列表可识别并简化错误提示；不同工作空间允许重名则避免不必要的全局冲突。
- Alternatives considered:
  - 全局应用名称唯一：限制过强，和个人空间隔离模型不匹配。
  - 允许同名并依靠时间区分：降低卡片识别效率并增加测试复杂度。
  - 自动追加序号：容易让用户误解真实应用名称。

## 决策 4：首版应用管理只覆盖创建、列表、详情和名称/说明编辑

- Decision: 应用实体首版支持创建、卡片列表、详情读取、编辑名称和说明；不提供删除应用，不提供状态人工编辑。
- Rationale: 规格澄清已限定可编辑字段为名称和说明，并明确不包含删除。状态可作为系统展示字段保留，首版由系统维护，避免引入额外状态机和误操作恢复问题。
- Alternatives considered:
  - 支持删除：需要删除确认、数据恢复、审计和关联流程清理，超出首版。
  - 支持状态编辑：状态语义未进入规格，容易影响后续发布/运行能力。
  - 仅支持创建不支持编辑：不符合澄清结果。

## 决策 5：编排画布首版使用静态空画布和入口，不引入画布引擎

- Decision: 应用详情右侧展示空画布状态和开始编排入口，不支持节点新增、移动、连接、删除、保存、运行或调试，也不引入第三方画布/流程库。
- Rationale: 澄清结果选择了最小画布边界。当前首版目标是建立应用详情布局与后续扩展入口，不需要承担流程编辑复杂度；不新增依赖也符合 AGENTS 约束。
- Alternatives considered:
  - 手写基础节点编辑：会引入未确认的交互和数据模型复杂度。
  - 引入 React Flow 等库：需要新增依赖，且超出首版能力。
  - 完整流程运行/调试：明显超出当前范围。

## 决策 6：数据库升级采用显式幂等迁移脚本并复用现有 SQLite 文件

- Decision: 复用现有 `RESULT_DB_PATH` 指向的 SQLite 文件，新增 `workspaces` 与 `workspace_applications` 表及必要唯一索引；通过 `server/scripts/migrate_workspace_schema.py` 和 `workspace_migrations.py` 提供幂等建表与验证。
- Rationale: 现有认证和 demo 数据已经复用同一 SQLite 本地数据库入口。继续复用可降低本地配置复杂度，并满足 AGENTS 对 schema 变更必须有升级路径、回滚路径和验证方式的要求。
- Alternatives considered:
  - 新增单独 workspace 数据库：会增加配置和本地启动复杂度。
  - 仅运行时自动建表：缺少显式数据升级和人工验证入口。
  - 引入 Alembic：需要新增依赖和迁移框架配置，超出当前批准范围。

## 决策 7：接口契约采用当前项目的 REST + JSON 风格

- Decision: 后端提供 `/api/workspace/current`、`/api/workspace/applications`、`/api/workspace/applications/{application_id}` 等 REST JSON 接口，错误响应沿用现有 `{detail: {code, message}}` 语义。
- Rationale: 当前认证接口已使用 FastAPI REST 风格、Pydantic 请求模型和统一错误 envelope。保持同一模式可减少前端 HTTP 封装变化，并便于契约测试复用。
- Alternatives considered:
  - GraphQL：新增技术栈且与现有接口风格不一致。
  - 单个聚合 POST 接口：会降低可测试性和语义清晰度。
  - 前端本地模拟工作空间：无法满足真实数据和权限验证要求。

## 决策 8：前端工作空间体验采用应用内页面状态，不引入路由依赖

- Decision: 首版在 `App.tsx` 中根据认证状态展示工作空间页面，并在 `workspace` feature 内用组件状态切换“工作空间卡片列表”和“应用详情左右分栏”；不新增路由库。
- Rationale: 当前项目尚未引入前端路由依赖，AGENTS 禁止未批准新增依赖。用组件状态即可满足“登录后进入工作空间、点击卡片进入详情”的首版验收路径。
- Alternatives considered:
  - 新增 React Router：需要新增依赖，当前范围不必要。
  - 使用浏览器 hash 手写路由：会增加非核心复杂度。
  - 保留认证页下方堆叠展示全部模块：不符合登录后默认进入工作空间的体验目标。

## 决策 9：验证策略组合契约、集成、单元、页面和日志/数据库检查

- Decision: 后端新增 workspace 契约测试、集成流程测试和领域/用例单元测试；前端至少通过类型检查、构建和浏览器页面验证；真实验证读取后端日志和 SQLite 数据确认数据流转。
- Rationale: 本功能涉及认证用户、数据库 schema、权限隔离和前端关键路径，单一测试层不足以证明完成。AGENTS 明确要求修复/开发任务结合测试、日志、接口结果或运行状态验证。
- Alternatives considered:
  - 仅单元测试：无法覆盖 HTTP Cookie 会话和数据库链路。
  - 仅手工页面验证：难以稳定覆盖重名、无权访问和迁移幂等。
  - 只检查代码 diff：不符合项目验收标准。
