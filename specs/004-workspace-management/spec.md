# Feature Specification: 工作空间与成员管理

**Feature Branch**: `004-workspace-management`

**Created**: 2026-05-19

**Status**: Draft

**Input**: User description: "实现工作空间的功能 用户注册后默认会创建一个工作空间 不同工作空间直接数据完全隔离 工作空间内可以添加删除成员 成员在工作空间中分为管理者和成员两种角色"

## Clarifications

### Session 2026-05-20

- Q: 普通成员的数据权限边界是什么？ → A: 普通成员可以查看、创建、修改、删除当前工作空间内业务数据，但不能管理成员。
- Q: 存量用户和存量数据在启用工作空间后如何归属？ → A: 每个已有用户创建默认工作空间，并将其现有数据归入该工作空间。
- Q: 工作空间成员角色是否允许变更？ → A: 仅管理者可变更成员角色，但不能让工作空间失去最后一个管理者。
- Q: 多工作空间用户登录后默认进入哪个工作空间？ → A: 记住用户上次选择的工作空间；若已无权限，则进入任一仍可访问的工作空间。
- Q: 管理者通过什么标识添加已有用户？ → A: 管理者通过用户名添加已经注册的用户。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 注册后自动拥有工作空间 (Priority: P1)

新用户完成注册后，系统自动为该用户创建一个默认工作空间，并将该用户加入为该工作空间的管理者，使用户无需额外配置即可开始使用工作空间内的业务能力。

**Why this priority**: 工作空间是后续数据隔离和协作的基础，没有默认工作空间会导致新用户注册后无法进入主要业务流程。

**Independent Test**: 可以通过注册一个新用户并查看其进入系统后的可用工作空间、成员身份和默认角色来独立验证。

**Acceptance Scenarios**:

1. **Given** 一个未注册的用户，**When** 用户成功注册，**Then** 系统为其创建且仅创建一个默认工作空间，并将该用户设为该工作空间的管理者。
2. **Given** 一个刚注册成功的用户，**When** 用户进入系统，**Then** 用户默认处于其自动创建的工作空间上下文中。
3. **Given** 用户属于多个工作空间且曾选择过当前工作空间，**When** 用户重新登录，**Then** 系统默认进入该用户上次选择且仍有权限访问的工作空间。

---

### User Story 2 - 工作空间数据完全隔离 (Priority: P1)

登录用户只能查看和操作其当前工作空间中的数据。不同工作空间之间的数据、成员列表和业务记录互不可见，避免组织间数据泄露。

**Why this priority**: 数据隔离是工作空间能力的核心安全要求，必须在任何协作功能之前成立。

**Independent Test**: 可以创建两个工作空间及其成员，分别产生工作空间内数据，再验证任一用户无法在另一个未授权工作空间中查看、搜索、修改或删除数据。

**Acceptance Scenarios**:

1. **Given** 用户 A 仅属于工作空间 X，用户 B 仅属于工作空间 Y，**When** 用户 A 查看数据、成员或业务记录，**Then** 用户 A 只能看到工作空间 X 的内容。
2. **Given** 用户不属于某个工作空间，**When** 该用户尝试访问该工作空间的数据或成员信息，**Then** 系统拒绝访问并给出明确错误语义。
3. **Given** 同一个用户属于多个工作空间，**When** 用户切换当前工作空间，**Then** 用户看到的数据范围随当前工作空间变化，并且不会混入其他工作空间的数据。

---

### User Story 3 - 管理工作空间成员 (Priority: P2)

工作空间管理者可以将已有用户添加到工作空间，也可以将成员从工作空间中移除。普通成员可以查看自己所属工作空间和自己的成员身份，但不能管理成员。

**Why this priority**: 成员管理让工作空间支持协作，同时角色边界保证工作空间管理行为可控。

**Independent Test**: 可以使用一个管理者账号和一个普通成员账号验证添加成员、删除成员、角色权限限制和成员列表变化。

**Acceptance Scenarios**:

1. **Given** 用户是工作空间管理者，**When** 该用户通过用户名添加一个未加入该工作空间的已注册用户，**Then** 该用户被加入工作空间并获得指定角色。
2. **Given** 用户是工作空间管理者，**When** 该用户删除一个工作空间成员，**Then** 被删除用户立即失去该工作空间的数据访问权限，但其用户账号不被删除。
3. **Given** 用户是普通成员，**When** 该用户尝试添加或删除工作空间成员，**Then** 系统拒绝该操作并说明权限不足。

---

### User Story 4 - 区分管理者与成员角色 (Priority: P2)

工作空间成员在每个工作空间内拥有独立角色，角色分为管理者和成员。管理者拥有成员管理权限；普通成员可以查看、创建、修改、删除当前工作空间内业务数据，但不能添加成员、删除成员或更改成员角色。

**Why this priority**: 角色模型决定工作空间协作边界，必须明确以支持后续权限扩展。

**Independent Test**: 可以将同一用户加入不同工作空间并设置不同角色，验证其权限随工作空间上下文和角色变化。

**Acceptance Scenarios**:

1. **Given** 同一用户在工作空间 X 是管理者、在工作空间 Y 是成员，**When** 用户分别进入两个工作空间，**Then** 用户在每个工作空间内只获得对应角色的权限。
2. **Given** 工作空间内存在多个管理者，**When** 任一管理者管理成员，**Then** 操作按管理者权限正常执行。
3. **Given** 用户是工作空间管理者，**When** 该用户将成员角色变更为管理者或将管理者降级为成员，**Then** 系统按变更后的角色更新该用户在当前工作空间内的权限，并保证工作空间仍至少有一个管理者。

### Edge Cases

- 当注册流程的用户创建成功但默认工作空间创建失败时，系统必须避免用户处于无工作空间且不可恢复的状态，并向用户返回明确失败结果。
- 当管理者尝试重复添加已经属于当前工作空间的用户时，系统必须拒绝重复成员关系并说明原因。
- 当管理者尝试删除当前工作空间最后一个管理者时，系统必须拒绝操作，保证工作空间始终至少有一个管理者。
- 当管理者尝试将当前工作空间最后一个管理者降级为成员时，系统必须拒绝操作，保证工作空间始终至少有一个管理者。
- 当被删除成员当前正在使用该工作空间时，系统必须在后续访问中立即拒绝其继续访问该工作空间数据。
- 当用户上次选择的工作空间已不可访问时，系统必须自动进入该用户仍可访问的任一工作空间；若不存在可访问工作空间，必须显示无可用工作空间状态。
- 当用户尝试访问不存在、已无权限或不属于自己的工作空间时，系统必须返回明确错误语义，且不得暴露其他工作空间的数据细节。
- 当同一用户属于多个工作空间时，工作空间切换不得改变其他工作空间中的角色或成员关系。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在用户成功注册时自动创建一个默认工作空间。
- **FR-002**: 系统 MUST 将注册用户自动加入其默认工作空间，并赋予管理者角色。
- **FR-002a**: 系统 MUST 为启用工作空间前已存在的每个用户创建默认工作空间，并将该用户现有数据归入其默认工作空间。
- **FR-003**: 系统 MUST 保证每个工作空间拥有独立的数据范围，用户只能访问其所属工作空间内的数据。
- **FR-004**: 系统 MUST 要求所有工作空间内数据的查看、创建、修改和删除行为都基于明确的当前工作空间上下文。
- **FR-005**: 系统 MUST 支持用户在其所属的多个工作空间之间切换当前工作空间。
- **FR-005a**: 系统 MUST 记住用户上次选择的工作空间，并在用户重新进入系统时默认使用该工作空间；若该工作空间已不可访问，则默认进入该用户仍可访问的任一工作空间。
- **FR-006**: 系统 MUST 支持工作空间管理者通过用户名添加已注册用户为当前工作空间成员。
- **FR-007**: 系统 MUST 支持工作空间管理者在添加成员时指定角色，角色仅限管理者或成员。
- **FR-007a**: 系统 MUST 支持工作空间管理者将当前工作空间成员的角色变更为管理者或成员。
- **FR-008**: 系统 MUST 支持工作空间管理者从当前工作空间删除成员，删除成员不得删除该用户账号。
- **FR-009**: 系统 MUST 拒绝普通成员添加成员、删除成员或更改成员角色。
- **FR-009a**: 系统 MUST 允许普通成员查看、创建、修改和删除当前工作空间内业务数据。
- **FR-010**: 系统 MUST 拒绝创建重复的工作空间成员关系。
- **FR-011**: 系统 MUST 防止删除当前工作空间最后一个管理者，或将当前工作空间最后一个管理者降级为成员。
- **FR-012**: 系统 MUST 在成员被移出工作空间后立即取消其对该工作空间数据和成员信息的访问权限。
- **FR-013**: 系统 MUST 支持用户查看自己所属的工作空间列表、当前工作空间以及自己在各工作空间中的角色。
- **FR-014**: 系统 MUST 支持工作空间成员查看当前工作空间的成员列表和成员角色。
- **FR-015**: 系统 MUST 对所有越权访问和越权管理操作返回明确错误语义，不得泄露未授权工作空间的数据内容。
- **FR-016**: 系统 MUST 记录工作空间成员添加、删除和角色相关变更的可审计事件，事件内容应包含操作者、目标用户、目标工作空间、操作结果和发生时间。

### Key Entities

- **工作空间**: 表示一个独立的数据边界和协作范围，包含名称、创建者、创建时间、当前状态等关键信息。
- **工作空间成员关系**: 表示用户与工作空间之间的归属关系，包含用户、工作空间、角色、加入时间和成员状态。
- **工作空间角色**: 表示成员在某个工作空间内的权限级别，仅包含管理者和成员两种角色。
- **用户**: 表示可登录系统的个人账号，可属于一个或多个工作空间，并在不同工作空间中拥有不同角色。
- **工作空间内数据**: 表示归属于某个工作空间的数据对象，必须通过工作空间边界进行访问控制。
- **审计事件**: 表示工作空间成员管理相关的重要操作记录，用于追踪成员变更和权限相关行为。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的成功注册用户在首次进入系统时拥有且至少拥有一个可用工作空间。
- **SC-002**: 用户完成注册到进入默认工作空间的流程可在 2 分钟内完成。
- **SC-003**: 未授权用户访问其他工作空间数据的验证场景中，系统拒绝率达到 100%，且不会返回其他工作空间的数据内容。
- **SC-004**: 管理者添加或删除一个工作空间成员的常规流程可在 1 分钟内完成。
- **SC-005**: 普通成员尝试执行成员管理操作时，系统拒绝率达到 100%，并向用户呈现可理解的权限不足原因。
- **SC-006**: 在包含至少 3 个工作空间、每个工作空间至少 3 名成员的验证数据中，成员列表、角色和工作空间内数据均只显示当前工作空间范围内的内容。

## Assumptions

- 默认工作空间名称可由系统根据用户信息生成，用户后续是否可重命名不属于本规格范围。
- 本规格仅覆盖已有用户加入工作空间，不覆盖通过邀请链接、邮件邀请或外部身份系统邀请新用户注册。
- 成员删除表示移出工作空间，不表示删除用户账号或清除该用户在其他工作空间中的成员关系。
- 管理者和成员是当前版本唯一角色；更细粒度权限、所有者角色、访客角色和自定义角色不属于本规格范围。
- 工作空间内现有业务数据都需要纳入工作空间隔离范围；启用工作空间时，存量用户的现有数据归入该用户的默认工作空间，具体数据清单在后续计划阶段结合现有系统确认。
- 工作空间删除、归档、转让所有权和计费相关能力不属于本规格范围。
- 用户必须至少保留一个可访问工作空间；当用户失去某工作空间访问权后，系统应引导其进入其他可访问工作空间或显示无可用工作空间状态。
