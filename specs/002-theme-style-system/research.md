# 研究记录：项目主题样式系统

## 决策 1：主题源采用“全局语义 token + Tailwind 语义映射 + 共享样式入口”

- Decision: 以全局语义化 token 作为视觉单一事实来源，并通过现有 Tailwind 配置与共享样式入口消费这些 token。
- Rationale: 当前项目已经具备 `ui/src/shared/styles/index.css` 和 `ui/tailwind.config.ts`，这是最小改造路径；可以同时支撑全局 CSS、Tailwind utility 和共享组件复用，避免继续沿用 `ink/sand/ember/pine` 这类局部命名。
- Alternatives considered:
  - 只在 Tailwind 配置里声明颜色：难以表达阴影、圆角、间距和状态语义，且不利于全局主题层扩展。
  - 只写纯 CSS class，不做 token 抽象：会继续产生硬编码与样式漂移。
  - 新增第三方 design token 工具：超出当前需求，且违反“未经批准不得新增依赖”。

## 决策 2：AI-Flow 风格只抽取视觉原则，不逐像素复刻

- Decision: 抽取 AI-Flow 的轻量面板层级、柔和圆角、低噪声边框、明晰文本层级和克制强调色作为设计原则，而不是直接搬运具体 class 或色值。
- Rationale: 用户要求“参考 AI-Flow”，而规格明确聚焦项目主题系统；抽象视觉原则更适合作为长期可维护的项目主题基线，也能避免把第三方界面细节硬塞进现有页面结构。
- Alternatives considered:
  - 直接复刻 AI-Flow HTML class 结构：会与当前项目结构和语义命名冲突，且维护成本高。
  - 完全不参考现有风格：无法满足用户对风格方向的明确要求。

## 决策 3：基础组件覆盖范围以“高频页面骨架”优先

- Decision: 首批基础样式覆盖按钮、输入框、卡片、标签、导航项、筛选项和空态容器，并通过统一状态矩阵定义默认、悬停、聚焦、选中、禁用反馈。
- Rationale: 这些元素已在用户给出的 AI-Flow 片段和当前项目首页形态中反复出现，能最快支撑工作台、列表、筛选栏和信息卡片等高频页面搭建。
- Alternatives considered:
  - 一次性覆盖完整组件库：范围过大，不符合最小化实现原则。
  - 仅做 token，不做组件层：无法真正降低页面搭建成本，也不满足规格中的组件复用目标。

## 决策 4：现有页面采用“最小迁移 + 主题展示页双验证”

- Decision: 保留现有 bootstrap 首页的业务职责，对其共享组件和主容器进行最小主题化迁移；同时新增独立主题展示页或展示区集中验证 token 与基础组件状态。
- Rationale: 当前首页依赖后端健康检查和 Celery 状态，不适合作为唯一视觉验收样例；独立展示区便于完整覆盖组件状态，而最小迁移能证明主题系统不是孤立样板。
- Alternatives considered:
  - 只改首页：很难完整展示所有组件和状态。
  - 只做展示页，不改现有页面：无法验证主题接入真实业务页面的可用性。

## 决策 5：允许使用 shadcn/ui，但主题语义优先于组件库默认视觉

- Decision: 在用户已明确批准的前提下，允许使用 shadcn/ui 作为基础组件承载层，但项目级主题 token 仍然是视觉单一事实来源，shadcn/ui 组件需要服从主题语义而不是反过来主导视觉。
- Rationale: 这既满足项目技术栈约束，也能借助成熟组件结构减少重复搭建；同时通过 token 优先策略避免把主题系统退化成“换一套组件默认皮肤”。
- Alternatives considered:
  - 完全不使用 shadcn/ui：可行，但会放弃已获批准的组件复用机会。
  - 直接照搬 shadcn/ui 默认外观：无法满足 AI-Flow 风格抽象和项目主题统一目标。

## 决策 6：验证路径以构建校验和人工视觉验收为主

- Decision: 验证包含 `pnpm run typecheck`、`pnpm run build`、页面运行检查、关键交互状态检查和浏览器控制台检查，不强制新增前端组件测试。
- Rationale: AGENTS 明确前端不强制组件级测试，但必须至少通过页面运行、关键交互或浏览器日志验证；主题系统的主要风险在于视觉一致性和状态表达，这更适合通过展示页与人工验收确认。
- Alternatives considered:
  - 只跑构建：不足以证明交互和视觉结果正确。
  - 引入视觉回归工具：当前无批准依赖与配套设施，成本过高。
