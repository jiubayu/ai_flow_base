# Feature Specification: 前后端工程初始化与启停脚本

**Feature Branch**: `001-fullstack-bootstrap`

**Created**: 2026-05-16

**Status**: Draft

**Input**: User description: "完成前后端工程的工程结构初始化 确保前后端工程可以正常启动 并提供启停脚本"

## Clarifications

### Session 2026-05-16

- Q: “可正常启动”的服务范围是否包含 Celery worker？ → A: 包含前端、后端、Celery worker。
- Q: 工程可用性的最低验收深度是什么？ → A: 需要最小联通验证，前端可访问后端，后端可触发或识别 Celery 能力。
- Q: 启停脚本应采用哪种交付形态？ → A: 提供统一入口脚本，支持 start、stop、status 子命令。
- Q: Celery 的最小联通验证口径是什么？ → A: 后端发起一个最小示例任务，并由 Celery worker 实际接收处理。
- Q: 工程初始化是否包含依赖安装指引和配置模板？ → A: 包含依赖安装指引和配置模板，开发者自行填入必要配置。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 初始化并启动完整工程 (Priority: P1)

作为项目开发者，我可以在拿到仓库后按约定完成初始化，包括依赖安装和配置模板准备，并启动前端、后端与 Celery worker，通过最小联通验证确认工程骨架已经可用。

**Why this priority**: 这是后续所有业务开发的前置条件；如果工程无法启动，其他功能开发无法展开。

**Independent Test**: 在全新或清理后的开发环境中，按项目提供的步骤完成依赖安装、配置模板准备并启动前端、后端与 Celery worker，能够看到三个服务都进入可用状态并输出明确日志，且前端可访问后端、后端可发起一个最小示例任务并由 Celery worker 实际接收处理。

**Acceptance Scenarios**:

1. **Given** 开发者拿到代码仓库且具备约定的运行环境，**When** 按说明完成依赖安装、配置模板准备并启动后端服务，**Then** 后端服务能够正常运行并输出可辨识的启动成功日志。
2. **Given** 后端服务已可运行，**When** 开发者启动前端应用与 Celery worker，**Then** 前端应用能够正常运行并提供可访问的本地入口，且 Celery worker 能进入可接收任务状态。
3. **Given** 前端、后端与 Celery worker 均已启动，**When** 开发者执行最小联通验证，**Then** 前端能够访问后端，且后端能够发起一个最小示例任务并由 Celery worker 实际接收处理，从而确认工程骨架已准备好承载后续功能开发。

---

### User Story 2 - 使用统一脚本管理启停 (Priority: P2)

作为项目开发者，我可以使用统一入口脚本管理本地开发服务，通过 `start`、`stop`、`status` 等统一命令减少手工输入和环境差异带来的错误，并统一管理前端、后端与 Celery worker。

**Why this priority**: 在工程能启动后，统一脚本能显著降低启动成本，提高团队协作一致性。

**Independent Test**: 仅执行提供的统一入口脚本即可完成启动、停止和状态确认，无需开发者手动拼接底层命令。

**Acceptance Scenarios**:

1. **Given** 工程已完成初始化，**When** 开发者执行统一入口脚本的 `start` 子命令，**Then** 脚本会按预期启动前端、后端与 Celery worker，并输出清晰状态及最小联通验证入口。
2. **Given** 服务已由统一入口脚本启动，**When** 开发者执行 `stop` 子命令，**Then** 已启动的服务会被正确停止且不会留下误导性的成功信息。
3. **Given** 服务已由统一入口脚本管理，**When** 开发者执行 `status` 子命令，**Then** 能看到前端、后端与 Celery worker 的当前运行状态。
4. **Given** 启动前存在缺失环境或端口冲突，**When** 开发者执行统一入口脚本，**Then** 脚本会明确指出失败原因和处理方向。

---

### User Story 3 - 理解工程结构与边界 (Priority: P3)

作为项目开发者，我可以快速理解前端、后端、配置模板与公共脚本的目录边界和职责，以便在既定结构上继续迭代功能。

**Why this priority**: 明确结构可以避免后续开发时偏离项目约束，减少重复建设和错误放置代码。

**Independent Test**: 开发者仅通过目录结构与配套说明，即可定位前端入口、后端入口、配置模板位置、日志目录及脚本位置，并说明各自职责。

**Acceptance Scenarios**:

1. **Given** 开发者查看工程目录，**When** 查找前端、后端、配置模板和脚本入口，**Then** 能在约定位置找到对应模块且职责清晰。
2. **Given** 开发者准备新增功能，**When** 参考目录说明进行放置，**Then** 不需要额外猜测工程边界或依赖启动顺序。

### Edge Cases

- 当开发者只启动后端、只启动前端或遗漏 Celery worker 时，系统如何给出当前可用范围、缺失依赖提示以及最小联通验证不可执行的说明？
- 当本地端口被占用、环境变量缺失或依赖未安装完成时，初始化或启动流程如何明确失败原因？
- 当统一脚本被重复执行时，如何避免重复启动、重复停止或残留失效进程信息？
- 当前端、后端或 Celery worker 中任一服务启动失败而其他服务已启动时，如何保证失败结果可见且便于开发者清理现场？
- 当配置模板存在但开发者未填写必要配置时，系统如何阻止误启动并明确指出缺失项？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供清晰的前端、后端和脚本目录结构，使开发者能够直接识别各模块职责与入口位置。
- **FR-002**: 系统必须支持开发者在受支持的本地开发环境中完成前端工程初始化。
- **FR-003**: 系统必须支持开发者在受支持的本地开发环境中完成后端工程初始化。
- **FR-003A**: 系统必须提供前端、后端与 Celery worker 所需的依赖安装指引和配置模板。
- **FR-004**: 系统必须允许开发者分别启动前端应用、后端服务与 Celery worker，并通过明确日志判断各自是否启动成功。
- **FR-005**: 系统必须提供统一入口脚本，用于按约定管理前端、后端与 Celery worker。
- **FR-006**: 统一入口脚本必须至少支持 `start`、`stop`、`status` 三类子命令。
- **FR-007**: 系统必须在初始化、启动和停止过程中，对缺失前置条件、端口冲突、服务启动失败和重复执行等场景给出明确错误语义。
- **FR-008**: 系统必须提供可执行的工程使用说明，覆盖初始化、启动、停止、日志查看与基础验证步骤。
- **FR-008A**: 系统必须在说明或脚本输出中明确区分“配置模板已提供”和“真实必要配置仍需开发者填写”。
- **FR-009**: 系统必须为前端与后端保留符合项目约束的扩展边界，使后续功能开发可以在现有结构上继续演进而无需重组目录。
- **FR-010**: 系统必须支持开发者验证工程骨架已正确启动，包括前端、后端与 Celery worker 至少一种可重复执行的最小联通验证方式。
- **FR-013**: 系统必须提供最小联通验证能力，至少覆盖前端访问后端，以及后端发起一个最小示例任务并由 Celery worker 实际接收处理两个方向。
- **FR-011**: 系统必须将启动与失败日志输出到可定位的位置，以支持开发者排查问题。
- **FR-012**: 系统不得通过静默兜底隐藏初始化失败、启动失败或停止失败结果。

### Key Entities *(include if feature involves data)*

- **工程模块**: 表示前端应用、后端服务、Celery worker 及其配套脚本目录的职责边界与入口关系。
- **启动任务**: 表示一次初始化、启动、停止或健康检查动作，包含目标服务、执行结果和日志位置。
- **联通验证**: 表示用于确认前端、后端与 Celery worker 已具备基础协作能力的最小验证动作及其结果，其中包含一个由后端发起并被 Celery worker 实际处理的最小示例任务。
- **运行状态**: 表示某个本地服务当前是否已初始化、是否正在运行、是否启动失败以及对应的诊断信息。
- **开发者说明**: 表示用于指导开发者完成初始化、通过统一入口脚本执行启停与状态检查，以及完成验证的文档化步骤集合。
- **配置模板**: 表示用于指导开发者补齐本地必要配置的模板文件及其必填项说明。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新开发者在具备受支持环境的前提下，可在 15 分钟内完成工程初始化并启动前端、后端与 Celery worker。
- **SC-001A**: 新开发者在首次进入仓库后，可在 5 分钟内定位依赖安装步骤和配置模板位置，并完成必要配置填写准备。
- **SC-002**: 100% 的本地启动尝试都能输出明确的成功或失败结果，不出现无结论的沉默状态。
- **SC-003**: 开发者可仅通过统一脚本在 3 分钟内完成一次完整的启动或停止操作。
- **SC-007**: 开发者无需查阅底层服务命令，仅通过统一入口脚本即可完成启动、停止和状态检查，首次执行成功率达到 100%。
- **SC-004**: 至少 90% 的常见环境问题（缺失依赖、端口冲突、重复启动、重复停止）可通过脚本输出直接定位到责任服务或前置条件。
- **SC-005**: 开发者在阅读工程说明后，可在首次尝试中成功找到前端入口、后端入口、日志位置和启停脚本位置，成功率达到 100%。
- **SC-006**: 开发者在服务启动后，可在 5 分钟内完成一次最小联通验证，并明确确认前端到后端、后端发起任务到 Celery worker 实际处理两个方向均可用。

## Assumptions

- 本功能面向项目开发者和协作者，而非终端业务用户。
- 本次范围聚焦本地开发工程骨架、基础可运行性和启停管理，不包含具体业务页面、业务接口或生产部署流程。
- 本次范围要求最小联通验证，但不要求完整业务功能或复杂异步任务编排；Celery 仅需完成最小示例任务处理。
- 前端、后端与 Celery worker 均需要独立的运行入口和基础日志能力，其中 Celery worker 可以与后端共享后端工程目录边界。
- 开发者具备项目约定的基础运行环境，并拥有在本地安装依赖与执行脚本的权限。
- 统一脚本只负责管理本地开发所需服务，不负责远程环境、生产环境或云端资源编排。
- 统一脚本以单一入口形式提供，并通过子命令区分启动、停止和状态检查。
- 配置模板可以提供占位示例，但不得假定真实敏感配置已自动可用。
