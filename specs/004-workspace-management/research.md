# Research: 工作空间与成员管理

## Decision: 新增 workspace 领域而不是扩展 auth 领域承载所有规则

**Rationale**: 工作空间是长期业务边界，包含成员关系、角色、当前工作空间偏好、审计事件和数据隔离规则。将其放入独立 domain/application 模块能保持认证用例聚焦登录注册，会话只引用 workspace 上下文。注册流程通过应用层编排创建默认工作空间，符合 DDD + 整洁架构。

**Alternatives considered**:

- 在 auth 领域直接增加 workspace 字段：短期简单，但会把协作和权限规则耦合到认证模块。
- 仅在 API 层处理 workspace：违反业务逻辑不得依赖基础设施和表现层的约束，难以测试。

## Decision: SQLite schema 使用独立表 `workspaces`、`workspace_memberships`、`user_workspace_preferences`、`workspace_audit_events`

**Rationale**: 独立表可以表达工作空间、成员关系、用户偏好和审计事件的生命周期。成员关系表以 `(workspace_id, user_id)` 唯一约束防止重复添加；角色通过受限字符串表达 `manager` / `member`；偏好表记录用户上次选择的工作空间，登录或会话刷新时可校验是否仍可访问。

**Alternatives considered**:

- 在 `user_accounts` 直接加 `workspace_id`：无法支持一个用户属于多个工作空间。
- 用 JSON 列保存成员列表：查询、唯一性、并发约束和迁移验证都更弱。

## Decision: 存量用户迁移为每个用户创建默认工作空间并回填现有数据归属

**Rationale**: 规格明确要求存量数据归入默认工作空间。迁移应先新增兼容 schema，再为无默认工作空间的用户创建默认工作空间和管理者成员关系，最后对已有业务表补充工作空间归属。当前代码中可确认认证表已存在；其他业务数据清单需在实施时按现有表逐一列出并加入验证 SQL。

**Alternatives considered**:

- 只对新用户生效：会造成存量用户无工作空间或数据无归属。
- 保持存量数据全局可见：违反数据完全隔离要求。
- 手工分配：不可重复、不可自动验证，不符合数据升级规范。

## Decision: 注册流程采用事务性创建用户、默认工作空间、管理者成员关系和会话

**Rationale**: 规格要求用户创建成功但默认工作空间失败时不能留下不可恢复状态。实现时应通过仓储事务或应用服务事务边界保证注册相关写入原子完成；失败时返回明确错误，并记录错误日志。若受现有仓储结构限制，应新增可事务化方法，而不是在 API 层分散执行。

**Alternatives considered**:

- 用户创建后异步创建工作空间：可能出现无工作空间窗口，违反 P1 验收。
- 创建失败后静默补偿：不符合禁止静默兜底和明确错误语义要求。

## Decision: 当前工作空间由服务端保存用户偏好并在会话响应中返回

**Rationale**: 多工作空间默认进入上次选择的工作空间；若无权限则进入任一仍可访问工作空间。服务端保存偏好能在不同浏览器和刷新流程中保持一致，并且可以在每次会话查询时校验成员关系。前端只展示和发起切换，不自行决定权限。

**Alternatives considered**:

- 仅前端 localStorage 保存：跨设备不一致，且移除成员后容易继续指向无权限工作空间。
- 每次登录手动选择：增加基础流程阻力，规格已选择记住上次选择。

## Decision: 管理者通过用户名添加已注册用户

**Rationale**: 当前认证模型以用户名作为注册和登录标识，添加成员通过用户名最贴合现有能力，避免引入邮箱邀请、搜索目录或外部身份依赖。本期只添加已注册用户，找不到用户名时返回明确错误。

**Alternatives considered**:

- 通过邮箱添加：当前用户名和 email 在注册实现中同值，但产品语义已是用户名登录，容易产生歧义。
- 系统用户列表选择：需要额外用户搜索/分页/隐私设计，不是本期必要范围。

## Decision: API 错误码使用明确业务语义

**Rationale**: 规格要求越权、重复成员、最后管理者保护、用户不存在等场景有明确错误语义。API contract 统一使用 `{detail: {code, message}}`，与现有认证错误响应一致，前端可直接展示可理解提示。

**Alternatives considered**:

- 仅 HTTP 状态码：不利于前端区分业务错误。
- 抛出通用 500：违反禁止吞没异常和明确错误语义。

## Decision: 普通成员拥有当前工作空间内业务数据常规 CRUD 权限，成员管理仅限管理者

**Rationale**: 规格澄清已确认该权限边界。实现上需要将工作空间成员身份解析为当前工作空间角色，数据访问验证只要求属于当前工作空间；成员管理、角色变更、成员删除要求管理者角色。

**Alternatives considered**:

- 普通成员只能读：不符合澄清结果。
- 普通成员只能操作自己创建的数据：需要对象所有者模型，超出当前两角色模型。
